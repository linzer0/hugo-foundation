# Hugo Foundation

A neutral, reusable Hugo content-model and View layer shared between Linar's
sites. Clone it for a runnable starter site; add it as a submodule to drop the
same View layer underneath your own content.

| Role | Where | Used by |
|---|---|---|
| Theme — what a consumer inherits | `layouts/`, `assets/`, `archetypes/` at the repository root | Consumers, through `theme:` |
| Site — this repository's own | `site/` | This repository, through `hugo --source site` |

The split is enforced by Hugo, not by discipline. A theme's `hugo.yaml` is
merged into every consuming build, and its `content/` is mounted into the
consuming site, so site material cannot live at the root. See
`docs/BASE-THEME.md` for the verified mechanism.

---

## Run the demo site

```bash
git clone --recurse-submodules https://github.com/linzer0/hugo-foundation.git
cd hugo-foundation
hugo server --source site
# → http://localhost:1313/
```

The site builds with no base theme (`--config site/hugo.yaml,site/hugo.no-base-theme.yaml`)
and again with the optional PaperMod submodule
(`--config site/hugo.yaml,site/hugo.with-base-theme.yaml`). CI runs both as
Gate 3.

## Add as a theme (consume)

This repository is **private**. The commands below assume you have been granted
access; without it the clone fails with a 404 rather than a permission error, so
if you hit that, ask for access (or make the repository public) before debugging
anything else.

```bash
git submodule add https://github.com/linzer0/hugo-foundation.git themes/hugo-foundation
```

CI hosts need the same access, and the default checkout will not have it. On
GitHub Actions, check out without submodules and fetch it with a token:

```yaml
- uses: actions/checkout@v4
  with:
    submodules: false
- name: Fetch hugo-foundation submodule
  env:
    SUBMODULE_TOKEN: ${{ secrets.SUBMODULE_TOKEN }}
  run: |
    git -c http.extraheader="AUTHORIZATION: basic $(printf 'x-access-token:%s' "$SUBMODULE_TOKEN" | base64)" \
      submodule update --init --recursive
```

Any other build host — a container image, a PaaS that builds on push — needs its
own equivalent, and will fail at the clone step rather than at the Hugo step. A
build host that cannot reach the submodule is the first thing to rule out when a
consumer's pipeline fails while the theme itself builds fine.

Such a host also needs Hugo Extended 0.167.0 or newer (see **Toolchain**).
Hosts that ship their own Hugo — Cloudflare's Workers build image defaults to
0.147.7 — silently fail below that with
`partial "./strings.html" not found`, which reads like a theme bug and is not
one.

`hugo.yaml`:

```yaml
theme:
  - hugo-foundation        # neutral View + content-model layer
  - PaperMod               # optional fallback theme (consumer-owned)
```

Order matters. Hugo resolves the project's `layouts/` first, then each theme
in the exact order listed; first match wins, and same-path templates are not
merged. A consumer with a reusable brand module places that before Foundation.
A consumer without PaperMod lists only `hugo-foundation`. See
`docs/CONTRACTS.md` §2 for the verified resolution table.

Then include Foundation's stylesheets from your head partial:

```go
{{ $components := resources.Get "css/components-base.css" | minify | fingerprint }}
<link rel="stylesheet" href="{{ $components.RelPermalink }}" integrity="{{ $components.Data.Integrity }}">
```

Override or layer brand-specific styles in the consumer site's CSS and
partials — every colour in Foundation is a `--fn-*` custom property.

## Where things go

The Foundation ships three content types, each opt-in per page:

| You want | Command | Where it lands | Front matter |
|---|---|---|---|
| Long-form article | `hugo new --kind bundle posts/my-article/index.md` | `posts/<slug>/index.md` (page bundle; cover next to it) | `type: article`, `date`, `description`, `tags`, `toc` |
| Short note | `hugo new --kind note notes/my-update.md` | `notes/<slug>.md` | `type: note`, `date`, `description`, `tags` |
| Static page (about, contact) | `hugo new --kind page about.md` | `about.md` | `type: page`, `description` |
| Dev Log entry | `hugo new --kind devlog content/devlog/2026-09-29-slug/index.md` | `devlog/<date-slug>/index.md` (page bundle) | `type: note` + `version`, `changes`, `tags: [devlog, …]` |

Pages that do not set `type:` keep your base theme's templates — the property
that makes it safe to drop Foundation alongside an existing site rather than
only in a greenfield one.

`public/` is never committed; it is the build output, regenerated by `hugo`.
The Foundation's own `public*` artifacts live under `fixtures/demo/` and are
gitignored.

Dev Log is a usage pattern of `type: note`, not a new content type. See
`docs/DEV-LOG.md`.

## Toolchain

Hugo **Extended 0.167.0**, pinned with SHA256 in `.github/workflows/ci.yml`.
A local green on a different Hugo is not a substitute.

```bash
hugo version          # must end with +extended and match 0.167.0
```

## Gates

Three local gates; CI runs all three on `ubuntu-latest` and `windows-latest`.

```powershell
powershell -File fixtures/build.ps1                # View layer renders identically across two skins
powershell -File fixtures/neutrality-check.ps1      # no brand names, analytics IDs, PaperMod selectors
hugo --source site --config site/hugo.yaml,site/hugo.no-base-theme.yaml --destination public-ci-no-base
hugo --source site --config site/hugo.yaml,site/hugo.with-base-theme.yaml --destination public-ci-pm
```

Linux / macOS: `bash fixtures/build.sh` and `bash fixtures/neutrality-check.sh`.
The site builds work on every platform.

CI is the final word. A green local run on a different Hugo version does not
count as a pass.

## Editing rules

- Do not add brand assets, site identity values, analytics IDs, or hard-coded host URLs to this repo.
- Keep component parameters generic. No component reads a specific front-matter key.
- Namespace everything: `fn-` classes, `--fn-*` tokens, `data-fn-*` hooks, `layouts/partials/fn/**`.
- Existing shortcode names are frozen; new parameters must default to today's output.
- Never add `layouts/_default/single.html` or `layouts/_default/baseof.html` — they shadow every page on every consumer.
- See `docs/CONTRACTS.md` and `docs/DEV.md` for the full rules.

---

## Upgrading

Pin a tag, move the submodule pointer, run the gates. `CHANGELOG.md` records
what counts as a breaking change, including the one that matters most here:
a Foundation template that widens which pages it renders.
